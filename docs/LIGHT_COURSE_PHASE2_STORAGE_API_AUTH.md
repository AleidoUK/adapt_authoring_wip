# Phase 2: Storage, API and Authorization

Part of the [Light Course Editor implementation plan](LIGHT_COURSE_IMPLEMENTATION_PLAN.md). See also the [plain-language guide](LIGHT_COURSE_EDITOR.md).

## Implementation status: done

All six collections, the `LightEditor` role, and optimistic-concurrency/validation/version-publish logic described below have been implemented and are covered by [test/lib.lightcoursemanager.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/test/lib.lightcoursemanager.js) (passing against a real Mongo instance). Two gaps in the shared framework were found and worked around **entirely within the new Light Course code**, without modifying the shared mechanisms themselves:

- **`ContentPlugin.prototype.retrieve` calls `hasPermission` with the literal action `"retrieve"`, not `"read"`.** Every `lib/role/*.json` file only ever grants `"read"`/`"create"`/`"update"`/`"delete"`, so a `hasPermission` override that falls back to `permissions.hasPermission(userId, action, resource)` for a genuinely role-based (non-owner, non-super-admin) user would always deny retrieval - `"retrieve"` never matches any statement's action list. This went unnoticed before because every existing content type's `hasPermission` either trivially allows everything (`courseasset`) or uses `helpers.hasCoursePermission`'s ownership/super-admin shortcuts, which never reach the mismatched literal action-string check. Worked around with [lib/lightcourse/permissionAction.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/lightcourse/permissionAction.js)'s `normalize()`, used by every new plugin's `hasPermission` before calling `permissions.hasPermission`. `create`/`update`/`delete` already pass the correctly-matching literal strings and need no mapping.
- **Asset deletion is not fully blocked by omitting `delete` from a role's `/api/asset/*` statement.** `lib/assetmanager.js`'s `createAsset()` automatically grants the *uploader* full CRUD (including delete) on their own specific asset via a per-user policy, independent of role - this is pre-existing, intentional behaviour for every content type (anyone can manage their own uploads), not something introduced here. An explicit `{"action":["delete"],"effect":"deny"}` statement on `/api/asset/*` was added to `lib/role/LightEditor.json` to override this (confirmed: `lib/permissions.js`'s `PolicyStatementParser` gives an explicit `deny` precedence over any `allow`, including one added later by a per-asset ownership policy), fully blocking light-editor asset deletion including of their own uploads, matching the main plan's "even by direct API request" requirement.
- The doc's original inline `LightEditor.json` snippet below used resource patterns like `lightcourse*` (no slash before the wildcard) - `lib/permissions.js`'s `captures()` matches wildcards as whole path segments only, so this would never actually have matched anything. The implemented role file below uses `lightcourse/*` (slash before the wildcard), matching every other existing role file's convention.
- **Updated during Phase 3**: `lightcourse.create()` now accepts an optional `_templateId`, applying `lightcoursetemplate`'s `contentSnapshot` (with freshly regenerated stable IDs via the shared [lib/lightcourse/idRegeneration.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/lightcourse/idRegeneration.js) helper) - the other direction of the "create from template" flow this phase's `lightcoursetemplate` section always intended but hadn't implemented yet. The `contentTree` root shape was also corrected to `{ children: [] }` (see the `lightcourse` section below) once Phase 3 needed to actually build a tree against it and found the original single-page-root shape couldn't represent a course's multiple pages.

## How new collections get registered (confirmed mechanism)

This backend auto-registers a Mongo collection for any plugin that follows the existing `ContentPlugin` contract - no manual Mongoose wiring needed:

- [lib/contentmanager.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/contentmanager.js)'s `ContentPlugin.onDatabaseCreated()` (~line 86-110) reads the plugin's `getSchemaPath()` (normally `plugins/content/<type>/model.schema`) and calls `database.addModel()`.
- The minimum viable plugin (confirmed against [plugins/content/courseasset/](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/plugins/content/courseasset)) is: `package.json` (just `displayName`/`version`), `index.js` (a constructor `util.inherits`-ing `ContentPlugin`, implementing `getModelName()`), and `model.schema` (draft-04 JSON Schema, same dialect as `plugins/content/course/model.schema`).
- Once registered this way, **the generic REST routes in `lib/contentmanager.js` (`POST/GET/PUT/DELETE /api/content/:type[/:id]`, confirmed at lines 773/795/929/998/1061) work automatically** for the new type - e.g. a `lightcourse` plugin gets `/api/content/lightcourse` CRUD for free, exactly as `course`/`article`/`block` do today. Custom actions (versioning, comparison, convert, bank attach) are added as extra routes registered in the plugin's own `initialize()`, the same way [plugins/content/course/index.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/plugins/content/course/index.js) adds `/my/course` and `/duplicatecourse/:id` beyond the generic CRUD.
- Plugin discovery itself is directory-based: [lib/pluginmanager.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/pluginmanager.js) `getPluginTypes()`/`getPlugins()` (~lines 46-132) scan `plugins/<type>/*` at startup - dropping a new folder under `plugins/content/` is sufficient, no central registry file to edit.
- Also added (not shared-framework behaviour, just used by the generic PUT route): `ContentConflictError` in [lib/contentmanager.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/contentmanager.js)'s exported `errors`, mapped to HTTP 409 by `PUT /api/content/:type/:id` - needed so `lightcourse`'s revision-guarded `update()` override (see **Concurrency** below) can actually surface a 409 through the existing generic route rather than a generic 500.

## New collections to create

Each is its own `plugins/content/<name>/` plugin, following the `courseasset` minimal pattern above plus the extra routes/hooks noted. **Implemented**: [plugins/content/lightcourse/](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/plugins/content/lightcourse), [plugins/content/lightcourseversion/](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/plugins/content/lightcourseversion), [plugins/content/lightcourseexport/](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/plugins/content/lightcourseexport), [plugins/content/lightcourseconfig/](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/plugins/content/lightcourseconfig), [plugins/content/lightcoursebankasset/](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/plugins/content/lightcoursebankasset), [plugins/content/lightcoursetemplate/](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/plugins/content/lightcoursetemplate).

### 1. `plugins/content/lightcourse/` - the draft
- `model.schema` fields: `_tenantId` (via the shared `tenantObject.schema` `$ref`, same ancestry as `course`'s `basicContent.schema` -> `tenantObject.schema` chain - more precise than `courseasset`'s plain `trackedObject.schema`, which has no `_tenantId` field at all), `title`, `revision` (an integer checked for optimistic concurrency - see **Concurrency** below), `contentTree` (nested page/article/block/component structure with per-node stable `_id` strings - do **not** reuse Mongo `ObjectId`s from a prior version so immutable versions keep their own IDs; stored as an opaque `{"type":"object"}` blob, like `component.model.schema`'s `_extensions`/`themeSettings` fields, since Mongoose's JSON-schema importer doesn't usefully constrain an arbitrarily-deep recursive tree), `pluginSelections` (`{ menu, theme, extensions: [] }`), `glossaryItems`/`resourceItems` (top-level arrays, each item requiring its own stable `_id` - minted server-side if omitted, validated for presence/uniqueness), `helpContent` (**added during Phase 4**: `{ popup: { title, body, instruction }, items: [] }`, matching the real `adapt-aleido-help` shape confirmed in [Phase 1](LIGHT_COURSE_PHASE1_SCHEMA_SPIKE.md) - a separate top-level field, not nested under `headerData`, since this is real translatable content carried through conversion rather than header metadata), `headerData` (opaque object - version history array, reviewing instructions, developer-info dropdowns, terminology, button/help-icon choices - see field list in [LIGHT_COURSE_EDITOR.md](LIGHT_COURSE_EDITOR.md); **new convention**: icon choices live at `headerData.iconChoices = { menuButton, reflection, help, drawer }`, validated against [Phase 1](LIGHT_COURSE_PHASE1_SCHEMA_SPIKE.md)'s icon table via [lib/lightcourse/iconOptions.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/lightcourse/iconOptions.js)), `currentVersionNumber`/`versionMajor`/`versionMinor`, `conversionStatus` (`none|converting|converted|failed`), `_convertedCourseId`, `createdBy`/`createdAt`/`updatedBy`/`updatedAt` (via the same `$ref` chain).
- Custom routes added in `initialize()`: `POST /api/content/lightcourse/:id/versions` (publish), `GET /api/content/lightcourse/:id/versions`, `GET /api/content/lightcourse/:id/versions/:versionId`, `GET /api/content/lightcourse/:id/versions/compare?a=&b=` (the `compare` route is registered *before* the `:versionId` route, otherwise Express would match the literal word `compare` as a version ID and the compare route would never be reached).
- `hasPermission()` override following [plugins/content/course/index.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/plugins/content/course/index.js)'s `CourseContent.prototype.hasPermission` pattern, but scoped to the light-editor resource (`/api/content/lightcourse/*`), **not** reusing `helpers.hasCoursePermission` (that function is tied to full-course sharing rules we don't want to inherit) - also denies `update`/`delete` once `conversionStatus === 'converted'` (the "locked after conversion" rule).
- `contentTree` shape (a Phase 2 decision needed to make hierarchy validation concrete, not pinned down anywhere else yet; **corrected during Phase 3** - a course contains *multiple* pages per the main plan, so the root cannot itself be a single page node): `{ children: [] }` at the root - a plain container, not a node - where each entry in the root `children` array is a `{ _id, type, children: [] }` node, `type` one of `page`/`article`/`block`/`component`, strictly nested in that order, a `block` may have at most two `component` children. Phase 3/4 should follow this shape when building the editor. See [lib/lightcourse/validation.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/lightcourse/validation.js) and [test/lib.lightcoursevalidation.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/test/lib.lightcoursevalidation.js).

### 2. `plugins/content/lightcourseversion/` - immutable snapshots
- `model.schema`: `_lightCourseId`, `versionNumber` (string, e.g. `"1.1"`), `contentSnapshot` (full copy of the draft's `contentTree`/`pluginSelections`/`glossaryItems`/`resourceItems` at publish time), `headerSnapshot`, `schemaFormatVersion` (integer - bump when the snapshot shape changes, so old versions can still be read/rendered after a future format change), `createdBy`, `createdAt`, `_convertedCourseId` (nullable).
- No update/delete routes exposed at all - enforce immutability at the `hasPermission` level (`update`/`delete` always `false` once the record is `create`d), not just by convention.
- Each exported document (Phase 5) also needs a point-in-time copy of rendered text + referenced images "keyed to that export/version" (per the main plan) - store this as a sibling record, [plugins/content/lightcourseexport/](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/plugins/content/lightcourseexport) with `_versionId`, `format` (`markdown|docx`), `renderedText`, `assetSnapshotRefs: []`, `exportedAt`, rather than mutating the version record after the fact - also immutable once created, for the same reason.

### 3. `plugins/content/lightcourseconfig/` - tenant-scoped admin configuration
- One record per tenant: default plugin selections, graphic placeholder per field, required non-text defaults (including representative video/audio media), icon choices for controls that have no sensible default.
- `hasPermission()`: only full-admin role can `create`/`update`; light editors get `read` only (to seed new-course defaults). No special-case code needed for this - the Light Editor role statement below only grants `read`, so delegating straight to the standard role/policy check already produces the right behaviour.

### 4. `plugins/content/lightcoursebankasset/` - bank membership (join collection)
- Directly modelled on the existing [plugins/content/courseasset/model.schema](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/plugins/content/courseasset/model.schema) (`_courseId`-style join: `_lightCourseId`, `_assetId`, `_fieldName`/`_nodeId`), but a **separate** collection from `courseasset` so full-course asset usage logic in [lib/assetmanager.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/assetmanager.js) is never silently affected by light-course rows (that file's `ASSET_USAGE_CONTENT_TYPES`/`assetUses()` scan, confirmed at lines 62/1432-1538, would need an explicit, deliberate addition of `lightcourse`/`lightcoursebankasset` if "used in light courses" should ever show in the existing asset-usage UI - **resolved as a product decision in [Phase 4](LIGHT_COURSE_PHASE4_COMPONENTS_PLUGINS_IMAGES.md)**: keep them separate, light courses get their own indicator).
- Attach/detach are just `create`/`destroy` on this collection; **no delete-from-bank route exists here** - that stays on the real `asset` collection via the existing `lib/assetmanager.js` delete path, gated by role (see **Permissions** below).

### 5. `plugins/content/lightcoursetemplate/` - templates
- `model.schema`: `name`, `description`, `contentSnapshot` (same shape as `lightcourseversion.contentSnapshot`), `createdBy`, `createdAt`. Single current snapshot per record (no template-level version history - confirmed as a product decision in the main plan, not a technical constraint).
- `hasPermission()`: `create`/`update`/`delete` admin-only; `read` available to any light editor (needed for the create-from-template picker in [Phase 3](LIGHT_COURSE_PHASE3_LIST_AND_EDITOR.md)). Same no-special-case-code reasoning as `lightcourseconfig` above.
- "Promote an existing light course version into a template" is a custom route (`POST /api/content/lightcoursetemplate/from-version/:versionId`) that copies `lightcourseversion.contentSnapshot` into a new template record with freshly generated stable node IDs, via the shared [lib/lightcourse/idRegeneration.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/lightcourse/idRegeneration.js) helper (also needed, per the main plan, when creating a light course from a template - not yet built, since that's a Phase 3 editor-flow concern, but the regeneration helper itself is ready to be reused there).

## Concurrency (optimistic concurrency, confirmed requirement from the main plan)

There is no existing optimistic-concurrency helper in this codebase to reuse (confirmed: `lib/contentmanager.js`'s generic `PUT /api/content/:type/:id` does a plain `db.update` with no version check). Implement a `revision` integer on `lightcourse`: every save (`PUT`) and version-publish (`POST .../versions`) must include the client's last-known `revision` in the request; the server does an atomic `findOneAndUpdate({ _id, revision: clientRevision }, { $set: ..., $inc: { revision: 1 } })`-style conditional update (available via the Mongoose layer in [lib/dml/mongoose/index.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/dml/mongoose/index.js)) and returns a 409 Conflict if no document matched. Version publish additionally re-reads the current `currentVersionNumber`/latest `lightcourseversion` inside the same conditional-update boundary so two simultaneous "create version" calls can't both succeed with the same number.

## Permissions and roles

Confirmed mechanism: [lib/role/*.json](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/role) files list `{resource, action, effect}` statements against `urn:x-adapt:{{tenantid}}/api/...` resources; [lib/rolemanager.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/rolemanager.js)'s `installDefaultRoles`/`syncDefaultRoles` (~lines 454-550) read every file in that directory and upsert by `name` - new role files are picked up automatically, and **existing role file edits need their `version` bumped** to be re-synced to already-provisioned tenants.

**Implemented** as [lib/role/LightEditor.json](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/role/LightEditor.json) (shown here with the `lightcourse/*`-style slash-before-wildcard fix and the asset-delete `deny` override, both explained in **Implementation status** above):
```json
{
  "name": "Light Editor",
  "version": "0.0.1",
  "statement": [
    { "condition": {}, "resource": "urn:x-adapt:{{tenantid}}/api/content/lightcourse/*", "action": ["create", "read", "update", "delete"], "effect": "allow" },
    { "condition": {}, "resource": "urn:x-adapt:{{tenantid}}/api/content/lightcourseversion/*", "action": ["create", "read"], "effect": "allow" },
    { "condition": {}, "resource": "urn:x-adapt:{{tenantid}}/api/content/lightcourseexport/*", "action": ["create", "read"], "effect": "allow" },
    { "condition": {}, "resource": "urn:x-adapt:{{tenantid}}/api/content/lightcoursebankasset/*", "action": ["create", "read", "delete"], "effect": "allow" },
    { "condition": {}, "resource": "urn:x-adapt:{{tenantid}}/api/content/lightcoursetemplate/*", "action": ["read"], "effect": "allow" },
    { "condition": {}, "resource": "urn:x-adapt:{{tenantid}}/api/content/lightcourseconfig/*", "action": ["read"], "effect": "allow" },
    { "condition": {}, "resource": "urn:x-adapt:{{tenantid}}/api/asset/*", "action": ["create", "read"], "effect": "allow" },
    { "condition": {}, "resource": "urn:x-adapt:{{tenantid}}/api/componenttype/*", "action": ["read"], "effect": "allow" },
    { "condition": {}, "resource": "urn:x-adapt:{{tenantid}}/api/extensiontype/*", "action": ["read"], "effect": "allow" },
    { "condition": {}, "resource": "urn:x-adapt:{{tenantid}}/api/menutype/*", "action": ["read"], "effect": "allow" },
    { "condition": {}, "resource": "urn:x-adapt:{{tenantid}}/api/themetype/*", "action": ["read"], "effect": "allow" },
    { "condition": {}, "resource": "urn:x-adapt:{{tenantid}}/api/user/me", "action": ["read", "update"], "effect": "allow" },
    { "condition": {}, "resource": "urn:x-adapt:{{tenantid}}/api/asset/*", "action": ["delete"], "effect": "deny" }
  ]
}
```
Key point, confirmed from [lib/assetmanager.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/assetmanager.js) (`hasPermission`/`destroyAsset`, lines 159-162/290-333): asset delete is checked purely against the `urn:x-adapt:{{tenantid}}/api/asset/<id>` resource. **Update to the original plan, confirmed during implementation**: simply omitting `delete` from `/api/asset/*` (as `lib/role/CourseCreator.json` does) is **not** sufficient on its own - `createAsset()` separately grants the uploader a per-asset `allow` policy that would otherwise let a light editor delete their own uploads regardless of role. The explicit `deny` statement above (evaluated before any later per-asset `allow`, since `PolicyStatementParser` gives `deny` precedence) is what actually closes this. Full admin convert/configure routes (`.../defaults`, `.../convert`) are protected by requiring `SuperAdmin`-equivalent permission on a dedicated resource, e.g. `urn:x-adapt:{{tenantid}}/api/content/lightcourse/*/convert`, granted only in `lib/role/SuperAdmin.json`'s existing wildcard statement - no separate admin-role file needed since `SuperAdmin.json` already grants `*`.

Do **not** add `lightcourse*` resources to `lib/role/CourseCreator.json` - per the main plan, full-course editors should not automatically gain light-course access.
