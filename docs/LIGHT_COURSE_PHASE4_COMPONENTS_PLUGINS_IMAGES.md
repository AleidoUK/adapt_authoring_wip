Depends on [Phase 1](LIGHT_COURSE_PHASE1_SCHEMA_SPIKE.md) (schema matrix), [Phase 2](LIGHT_COURSE_PHASE2_STORAGE_API_AUTH.md) (bank join collection, config collection) and [Phase 3](LIGHT_COURSE_PHASE3_LIST_AND_EDITOR.md) (scaffold reuse).

## Implementation status: done, with one real Phase 3 bug fixed and some scoping decisions

Validated via `grunt handlebars:compile`, `less:dev`, `generate-lang-json` and `requirejs:dev` (all succeed, bundle includes every new file) plus the full backend suite (92 passing / the same 14 pre-existing unrelated failures as every prior clean run - confirmed no regressions from the `lightcourse` schema/validation changes below). No live browser session - see the **Manual QA checklist** at the end of this document.

**A real bug found and fixed**: [Phase 3](LIGHT_COURSE_PHASE3_LIST_AND_EDITOR.md)'s component form view passed its filtered schema straight to `new Backbone.Form(...)` with JSON-schema `type` values (`"string"`/`"array"`/`"object"`) untouched. Backbone.Form itself resolves a string `schema[key].type` by looking it up as a key in `Backbone.Form.editors` (confirmed in `frontend/src/libraries/backbone-forms.js`) - so it needed the *editor name* (`"Text"`/`"List"`/`"Asset:image"`), not the raw JSON-schema type, and would have thrown on every real field render. Fixed by exporting `modules/scaffold/index.js`'s existing `buildSchema()`/`generateFieldObject()` mapping logic as a new public `Origin.scaffold.buildSchema()`, called from [lightCourseComponentFormView.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/frontend/src/modules/lightCourseEditor/views/lightCourseComponentFormView.js) - genuinely reusing scaffold's logic as this phase's doc always intended, rather than reimplementing it.

**The shared `Asset:image`/`Asset:audio` editor (`scaffoldAssetView.js`) cannot be reused either** - it calls `Origin.scaffold.getCurrentModel()` and writes to the full-course `courseasset` collection, neither of which apply outside the full editor (confirmed: `assetManagementModalView.js`'s `postRender` also unconditionally calls `Origin.scaffold.getCurrentModel()`, so the full asset-browsing modal isn't reusable either). [schemaFilter.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/frontend/src/modules/lightCourseEditor/schemaFilter.js) now remaps any kept `Asset:<type>` field to `LightCourseAsset:<type>`, a new editor ([lightCourseBankAssetFieldView.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/frontend/src/modules/lightCourseEditor/views/lightCourseBankAssetFieldView.js)) that browses/uploads via the real `/api/asset` endpoints and attaches via `lightcoursebankasset`, scoped by light-course ID via a small shared context singleton ([lightCourseAssetContext.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/frontend/src/modules/lightCourseEditor/lightCourseAssetContext.js) - the same pattern scaffold's own `currentModel` uses, since Backbone.Form editors are instantiated generically with no constructor options pass-through).

**Audio field path corrected**: the real `adapt-aleido-audio/properties.schema` merges onto every component's schema at `_extensions._audio` (confirmed against the live installed extension, via the same `/content/schema` route mechanism Phase 1 analyzed), not a top-level `_audio` as originally assumed - fixed in `schemaFilter.js`. The extension's separate per-item audio array (`_audio._componentItems._items[]`, index-matched against the component's own unrelated item array) is **not** exposed - only the single component-level audio field is - a deliberate scope reduction given the bespoke cross-referencing UI it would otherwise need.

**Resources/help editors added, including a new `helpContent` model field**: with [Phase 1](LIGHT_COURSE_PHASE1_SCHEMA_SPIKE.md)'s resources-ID follow-up resolved, both the glossary and resources list editors are built using a new shared [lightCourseItemListView.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/frontend/src/modules/lightCourseEditor/views/lightCourseItemListView.js). The help extension's content (`_popup`/`_items[]`) is real translatable *content*, not header metadata, so it needed a new top-level `helpContent` field on [plugins/content/lightcourse/model.schema](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/plugins/content/lightcourse/model.schema) (plumbed through `lib/lightcourse/validation.js`'s item-ID checks, `idRegeneration.js`'s snapshot regeneration, and the version-publish snapshot) - built in [lightCourseHelpView.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/frontend/src/modules/lightCourseEditor/views/lightCourseHelpView.js). All three are gated on their extension being selected, per the main plan.

**Not built this pass**: a per-item asset attachment for resource entries beyond the plain `_link` text field (the product doc's "resource ID value" is the entry's own stable `_id`, which already exists - confirmed not conflated with a separate asset reference). Revisit if real usage shows editors need to attach an actual bank asset to a resource entry rather than a freeform link/path.

## Component type list and form rendering

Populate the "add component" picker from `GET api/componenttype` (already permitted to the Light Editor role per [Phase 2](LIGHT_COURSE_PHASE2_STORAGE_API_AUTH.md)) - this is the same source the full editor's component picker uses, confirmed via [frontend/src/modules/editor/contentObject/views/editorPageComponentListView.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/frontend/src/modules/editor/contentObject/views/editorPageComponentListView.js) (`this.model.get('componentTypes')`, filtered on `_isAvailableInEditor`). No new backend endpoint is needed here.

As established in [Phase 3](LIGHT_COURSE_PHASE3_LIST_AND_EDITOR.md), render the actual field editor via `Origin.scaffold.buildForm({ model })` ([frontend/src/modules/scaffold/index.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/frontend/src/modules/scaffold/index.js)), not a bespoke renderer. Concretely:

1. Before calling `buildForm`, filter the component's resolved schema (from `Schemas(type)` in [frontend/src/modules/scaffold/schemas.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/frontend/src/modules/scaffold/schemas.js)) down to fields where `field.translatable === true` (or `field._adapt && field._adapt.translatable`, per the Phase 1 dialect split), or `field.inputType` is `Asset:image`/an audio equivalent, or the field is `uniqueId`-mapped (which per Phase 1 is `_extensions._uniqueId._id`, not a literal top-level `uniqueId` key - the filter needs an explicit path remap for this one field). Settings/style/layout fields (e.g. `_classes`, `_isOptional`, `themeSettings`, confirmed present on every component in [plugins/content/component/model.schema](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/plugins/content/component/model.schema)) are excluded entirely - the light editor never exposes them.
2. Nested item arrays (e.g. `adapt-aleido-help`'s `_items[]`, confirmed in [Phase 1](LIGHT_COURSE_PHASE1_SCHEMA_SPIKE.md)) already render through Backbone-Forms' `List` editor (`generateFieldObject` maps JSON-schema `array` -> `List`, confirmed in [frontend/src/modules/scaffold/index.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/frontend/src/modules/scaffold/index.js)) - add/remove-item "for free" via the existing `list.hbs`/`listItem.hbs` templates, filtered the same way as (1) for each item's own fields.
3. Add `Graphics Notes` and `Developer Notes` as two extra fields merged into the filtered schema at render time (not stored in the installed component's own schema - store them on the `lightcourse` content-tree node record itself, alongside but clearly separated from the component's own field values, so they're trivially excludable from word counts/conversion per [Phase 5](LIGHT_COURSE_PHASE5_WORDCOUNTS_EXPORTS.md)/[Phase 7](LIGHT_COURSE_PHASE7_ADMIN_CONVERSION.md)).
4. **Do not expose video/audio selection** beyond the gated audio field below, per the product doc.

## Removed/upgraded plugin handling

The component-type list (`componenttype` records) persists independently of whether a component is still installed (confirmed: these are DB records populated at install time via [lib/bowermanager.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/bowermanager.js), not derived live from the filesystem). If a `lightcourse` tree node's `_component` value has no matching `componenttype` record, render its stored field values read-only using the schema snapshot kept in the node itself (per the main plan's "keep a snapshot of the field descriptors" requirement) rather than failing to render. Show a "missing plugin" banner; block conversion ([Phase 7](LIGHT_COURSE_PHASE7_ADMIN_CONVERSION.md)) until resolved. On upgrade, newly-added `translatable` fields simply appear next time the node is opened, since the filter in step 1 above re-evaluates the *current* installed schema on every render - no migration needed for this case, only for genuinely removed fields (never erase unknown fields on save, per the main plan).

## Image/audio bank

Reuse the existing asset pipeline, scoped by the new `lightcoursebankasset` join collection ([Phase 2](LIGHT_COURSE_PHASE2_STORAGE_API_AUTH.md)):

- Upload: `POST api/asset` (existing endpoint, confirmed in [lib/assetmanager.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/assetmanager.js), already permitted to the Light Editor role per Phase 2's `create` grant on `/api/asset/*`).
- Attach to course: `POST api/content/lightcoursebankasset` with `{_lightCourseId, _assetId, _fieldName/_nodeId}`.
- Detach from course: `DELETE api/content/lightcoursebankasset/:id` - removes only the reference, never the underlying asset.
- Bank listing: `GET api/asset/query` (existing, tenant-scoped already).
- **Deletion from the bank is intentionally not exposed to light editors** - confirmed as a role-grant omission, not new logic: [lib/role/CourseCreator.json](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/role/CourseCreator.json) already omits `delete` on `/api/asset/*` (line 8) to the same effect, and the new `LightEditor.json` role (Phase 2) does the same. [lib/assetmanager.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/assetmanager.js)'s `hasPermission`/`destroyAsset` (lines 159-162, 290-333) check only the resource string, with no uploader-vs-admin distinction built in - so this is enforced entirely by what the role grants, confirming light editors cannot delete bank images "even by direct API request" (acceptance scenario 4 in the main plan) as long as the role file is correct.
- Admin bank governance (removal, placeholder-per-field configuration) uses the existing admin-only asset-delete path plus the new `lightcourseconfig` collection (Phase 2) for placeholders/defaults - no new asset-deletion mechanism needed.
- **Resolved**: "asset used in a light course" does **not** surface in the existing full-course asset-usage UI (`assetUses()` in [lib/assetmanager.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/lib/assetmanager.js), lines 1432-1538, which scans `ASSET_USAGE_CONTENT_TYPES = ['component','article','block','contentobject','course','config','clipboard']`). Leave that scan untouched (light courses are a separate concern) and give the light editor its own "used in this course" indicator sourced from `lightcoursebankasset`; revisit unification only if real usage shows editors need a single cross-cutting view. **Implemented**: [lightCourseBankAssetFieldView.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/frontend/src/modules/lightCourseEditor/views/lightCourseBankAssetFieldView.js)'s bank browser badges each asset already attached to the current course, queried via the generic `GET api/content/lightcoursebankasset/query` route (no new backend endpoint needed - every content plugin gets this for free, confirmed in [Phase 2](LIGHT_COURSE_PHASE2_STORAGE_API_AUTH.md)).

## Plugin selection (Menu/Theme/Extensions)

Populate from `GET api/menutype`, `GET api/themetype`, `GET api/extensiontype` (all already granted to the Light Editor role). Render as a simple selection list, not the full plugin-settings form - this is a deliberate scope reduction from the full editor's [frontend/src/modules/editor/menuSettings](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/frontend/src/modules/editor/menuSettings) / `extensions` modules, which should **not** be reused wholesale (they expose full per-plugin settings forms, which is exactly what this feature intentionally omits). ## Glossary/resources entries

Gate the glossary/resources list editors on `pluginSelections.extensions` containing the respective extension - if absent, show an explanatory message rather than the editor (per the main plan). Glossary entries map directly to `_glossary._glossaryItems[]` (`term`/`description`, confirmed in Phase 1) stored on the `lightcourse` document. **Resolved**: the Phase 1 follow-up confirmed no stable per-item ID exists anywhere in the real `adapt-contrib-resources` schema or runtime (items are addressed purely by array index) - so the light course's own `resourceItems[]._id` (minted server-side per [Phase 2](LIGHT_COURSE_PHASE2_STORAGE_API_AUTH.md)) *is* the "resource ID value" the product doc describes, not a separate field to find. Both editors are built using the shared [lightCourseItemListView.js](/home/laurahooper/Projects/AdaptAuthoring/aleido_authoring/frontend/src/modules/lightCourseEditor/views/lightCourseItemListView.js).

## Manual QA checklist

Builds on [Phase 3](LIGHT_COURSE_PHASE3_LIST_AND_EDITOR.md)'s checklist - run these specifically in a real browser session once that phase's navigation/list/tree checks pass:

- [ ] Open a component's field editor for a component with translatable items (e.g. one with nested `_items[]`) - confirm each item's fields render correctly (add/remove item rows work, text saves correctly) and that only translatable/asset fields appear, never settings/style fields.
- [ ] Confirm a component with a `uniqueId`-mapped extension shows a "Unique ID" field; one without does not.
- [ ] With the audio extension selected among the course's Extensions, confirm an audio field (upload/choose-from-bank + transcript) appears on components; deselect the extension and confirm it disappears.
- [ ] Choose an image field's "Choose from bank" - confirm it lists only images (not audio/other types), shows a "Used in this course" badge on assets already attached to this course, and that selecting one updates the preview thumbnail immediately.
- [ ] "Upload new" on an image/audio field - confirm the file uploads, becomes the field's value, and is attached to this course's bank (re-open "Choose from bank" and confirm it now shows as used).
- [ ] Simulate a removed plugin (clear/rename a `componenttype` record for a type already used in a saved course, or just pick an uninstalled-looking name) and confirm the node renders its last-known values read-only with a "missing plugin" message, rather than failing to render.
- [ ] Toggle the glossary extension on/off in Plugin selections - confirm the glossary editor appears/disappears accordingly (with the "extension not selected" message shown when off) without needing a page reload.
- [ ] Add/edit/reorder/remove glossary entries, then Save Draft + reload - confirm all changes persisted in order.
- [ ] Same checks for resources entries (including the `_type` dropdown and `_link` field) and for help content (popup title/body/instruction plus the items list with icon/title/body) - each gated correctly on its own extension.
- [ ] Confirm there is no "pop-up vs. graphic walkthrough" style choice anywhere in the help editor (per Phase 1's resolved finding).
