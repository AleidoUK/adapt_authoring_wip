## Scope and working model

- A light course is tenant-scoped structured content, separate from a full Adapt course. It has one editable draft, immutable numbered versions, selected plugins, and a conversion state.
- Light editors can list, create, edit, version, compare, import, and export all light courses in their tenant. They cannot open full-course management or delete bank assets.
- Existing full-course editors can see translatable word counts and export Markdown/Word for full courses; they do not gain light-course access solely from that role.
- Only full administrators configure light-course defaults, convert the latest light version, and edit the resulting full course. Conversion locks the light course only on success.
- The existing Adapt ZIP export/import remains unchanged. Document export/import is a separate workflow.

## Architecture and data contracts

Create separate models/collections for light courses, immutable versions, and tenant-scoped configuration and image-bank membership. Use the existing database, asset storage, authentication and permission conventions where they are suitable, without reusing the full-course CRUD endpoints for light content. Every API query and mutation must scope by tenant on the server, including reads by ID, image references, version retrieval, import, and export.

A light course draft should contain a stable course ID and revision token, title, ordered page/article/block/component tree, plugin choices, glossary and resources lists, selected bank image/audio references, current version pointer, creation/update metadata, conversion status and the document header data described below. Each content node and editable field needs a stable ID for document round trips and comparisons. A component records its plugin identity/version, its translatable fields/items, any selected graphic and audio references, and its non-translatable Graphics Notes and Developer Notes fields. Keep a snapshot of the field descriptors necessary to display old data when a plugin is later removed; never erase unknown or newly obsolete fields on save. Versions are immutable snapshots with a version number, creator, timestamp, content, plugin choices and schema/format version. Store source and resulting full-course IDs when converted.

The audio field on a component/item follows the same gating and shared-bank pattern already used for graphics, but is only shown when an audio extension is among the course's selected plugins; validate the referenced asset's type/size and tenant ownership the same way as image references.

Document header data sits alongside the content tree and is not itself translatable content: a version history list, free-text reviewing instructions, the developer-information dropdowns and checkbox (navigation linearity, full/standard layout, tracking criteria, reflection tool), the terminology dropdowns, and the button/help-screen icon choices. A version history entry has a version number, export date, author, free-text notes, a screen count, a word count and a free-text estimated duration; the version number, date, author and both counts are server-calculated and not user-editable, while notes and duration are editable. A "screen" is one component, so the screen count is simply the component count in the tree. A new version history entry is appended automatically when an exported document is re-imported, and can otherwise be added or edited directly by an editor. Exporting a document must also persist a point-in-time copy of its rendered text and any referenced images, keyed to that export/version, so earlier exports remain retrievable even after the draft changes further.

All document header data is informational and is not applied when generating the full course, with one exception: the button/help-screen icon choices are mapped onto the generated full course's navigation configuration during conversion, wherever the target theme/menu expose that setting. Validate the chosen icon identifiers against the target theme/menu's supported set as part of conversion preflight, and surface an actionable error if a chosen icon isn't supported rather than silently falling back to a default.

Glossary entries and resource entries are stable-ID content lists alongside the page/article/block tree, not components. A glossary entry holds its term and definition. A resource entry holds its translatable details plus a resource ID value, the identifier used elsewhere to reference that resource; validate it is present and unique within the course. Both lists only apply when the corresponding extension is among the course's selected plugins, and both are included in versions, comparisons, word counts and document export/import on the same terms as other translatable content.

The help extension's content is configuration, not a list: its popup text and, where the extension supports it, the separate help page the popup links to. Store it alongside the other selected-plugin configuration, gated on the help extension being selected, and carry it through versions, comparisons and conversion unchanged.

A course template is a separate, reusable record: a stable ID, name/description and a content snapshot in the same shape as a light course version (tree, plugin choices, starter glossary/resource entries). Creating a course from a template copies that snapshot into a brand-new draft with freshly generated stable IDs; the new draft has no ongoing reference to the template, so later edits to either never affect the other. Only administrators create, edit or remove templates; the simplest route is letting an admin promote any existing light course version into a new template record.

On creating the first version, use 1.0. From the latest version, a minor increment changes 1.0 to 1.1 (or 1.1 to 1.2); a major increment changes 1.1 to 2.0. Save only updates the unpublished draft. Creating a version checks the expected draft revision and latest version inside one consistency boundary so simultaneous editors cannot publish the same number. Import creates/updates an unpublished draft based on the latest version; publishing its chosen next version is a separate, explicit action. Define how an existing unsaved draft is handled before importing: require confirmation to replace it or require it to be saved/versioned first; never silently discard it.

Use the effective installed Adapt framework schemas for base content and installed component metadata for plugin fields. Component schemas can have nested objects and arrays: walk them recursively for `translatable` fields and graphic inputs. Respect required defaults and validation at conversion time. `uniqueId` is an editor-facing field whose mapping to the installed unique-ID extension and output schema must be confirmed during the schema spike. Keep component/plugin IDs stable even if display names change.

## Permissions and navigation

Add a dedicated Light Editor role and feature/API permissions. Full administrator access is checked separately for defaults and conversion. Do not give the Light Editor the existing Course Creator permission: it grants broad content and asset access. Do not assume hiding navigation is authorization. The current asset creation flow grants the asset creator delete permission; use a dedicated bank upload path/policy so a light editor cannot delete a shared bank image even if they uploaded it. Deleting from a course removes only that course's reference. Enforce the same rules at every download and asset-serving endpoint.

Route light editors to a list-first home, with a title-and-save create flow, edit button and title double-click. Restrict full dashboard, editor, settings, asset-management and export routes as well as their APIs. An admin may retain full navigation and enter the light area explicitly. Define feature visibility for users with multiple roles rather than relying on route order.

Template management (create, edit, promote-from-version, delete) is an admin-only action; template selection on the create flow is available to any light editor.

## Delivery phases

### 1. Schema and compatibility spike

Inspect installed base schemas, representative installed components with nested items, graphic fields and required media/settings, plus menu/theme/extension metadata. Determine how the unique-ID extension stores identifiers. Inspect the installed audio extension's schema to confirm how component/item audio fields are declared and stored. Inspect each installed theme/menu's navigation configuration to confirm which Vanilla font icon identifiers are valid for Next, Back, Menu, Help, Side Drawer and Reflection, so the Buttons header can offer only supported choices and conversion can map them reliably. Inspect the installed glossary and resources extensions: their course-level configuration shape, how resource items declare their ID field and whether it must be unique course-wide or tenant-wide, and how both extensions expect their item lists to be supplied on course creation. Inspect the installed help extension's configuration shape: how its popup text and any linked help page are stored, and whether the page is a separate content node or an embedded field. Record which fields need type-specific default values, how references are encoded, and whether any installed component imposes additional conversion constraints. Produce a field-mapping matrix and test fixtures before implementing the generic editor. This is a gate, not a promise that arbitrary third-party schemas require no special handling.

### 2. Storage, API and authorization

Add tenant-scoped persistence and migrations/setup for light drafts, immutable versions, light configuration, bank membership and templates. Add endpoints for listing/creating/retrieving/saving drafts, reordering nodes, publishing/listing/retrieving/comparing versions, bank selection/upload (images and audio), import/export, configuration, conversion, glossary/resource entry CRUD and reordering, help-extension content editing, document header data (version history add/edit, reviewing instructions, developer information, terminology, button/help-screen icon choices), and template listing/creation/promotion/deletion. Validate node hierarchy, a maximum of two components per block, the existence and tenant ownership of referenced assets, one Menu/one Theme selection, resource ID presence/uniqueness, and chosen icon identifiers against the relevant theme/menu, on the server. Use optimistic concurrency for draft edits, version creation, import and conversion. Test cross-tenant ID guessing, locked-course mutations, direct full-course API calls, forbidden bank deletion and cross-tenant template access.

### 3. Light-course list and editor

Build a dedicated frontend module using existing Backbone/Origin patterns. Show tenant-wide light courses as a list with title, updated date, latest version, draft/converted state and edit/review actions. Provide create, Save Draft, Create Version, edit and read-only review. The create flow offers a blank course or any available template; choosing a template clones its snapshot into the new draft with fresh stable IDs. The editor supports adding pages, articles, blocks and up to two components per block; reorder blocks and components in the tool, including left/right positions when paired. Preserve ordering as explicit data, not incidental database order. Provide useful empty, loading, conflict and validation states.

Render the document header sections at the top of the editor: a version history table (server-calculated Version/Date/Author/Screens/Words, editable Notes/Est. duration, plus a manual add-row action), reviewing instructions, developer information (navigation, layout and tracking dropdowns, reflection checkbox), terminology dropdowns, and the button/help-screen icon pickers with each control's first option as its default.

### 4. Components, plugins and images

Populate component choices from installed types; render common title, displayTitle, body, instruction and uniqueId fields where applicable, plus translatable nested item fields. Let users add/remove items. Show graphic selectors only where the effective schema declares a graphic field. Do not expose video/audio selection in the light editor. Populate a plugin list with exactly one selected Menu, one Theme and multiple selectable Extensions; seed new courses from admin-configured defaults (including bookmarking/uniqueId where installed and configured). Removed plugins remain recorded and read-only; upgraded plugins retain old content and expose newly translatable fields. Show a conversion warning for missing plugins or defaults.

Provide tenant image-bank listing/upload to light editors and admin-only removal from the bank. Images can be attached/detached from light courses. Admin configuration covers bank governance, default plugin selections, a placeholder for each graphic field and defaults for every required non-text setting, including representative video/audio media. Validate image type/size and references against existing upload limits; do not treat the presence of a default file as proof it satisfies a plugin schema.

Where an audio extension is among the course's selected plugins, show an audio field for components and their items, backed by a shared tenant audio bank with the same light-editor-upload/admin-only-deletion rules as the image bank. Keep this hidden when no audio extension is selected. Add Graphics Notes and Developer Notes free-text fields to every component, stored and displayed alongside its other fields but excluded from word counts, comparisons of translatable content, and conversion.

Where the glossary and/or resources extensions are among the course's selected plugins, provide a list editor for their entries: add, edit, reorder and remove, with the resource entry's ID field shown and validated for presence and uniqueness. If neither extension is selected, keep the lists hidden rather than letting editors populate content that conversion cannot place anywhere.

Where the help extension is among the course's selected plugins, provide an editor for its popup text and its linked help page content. If the extension isn't selected, keep this content hidden rather than letting editors populate content that conversion cannot place anywhere.

### 5. Shared translatable word counts and exports

Implement a server-side traversal of effective base/component schemas that selects each stored translatable string exactly once, including nested item fields, glossary entries and resource entries. Explicitly exclude Graphics Notes, Developer Notes and all document header fields from this traversal, since they are developer/reviewer-facing, not course content. Agree and test a word-count rule for HTML: strip markup, decode entities, normalize whitespace, exclude markup attributes and non-translatable fields, and use the same tokenizer for component and course totals. For full courses use the same service with the full-course access checks; totals include translatable text at course, page, article and block level as well as components, glossary and resources. Expose per-component counts, course totals, and the screen count (one per component) used by the version history table; test multilingual and rich-text examples.

Export version snapshots as Markdown and `.docx`, including structure, editable text/allowed formatting, stable IDs, word counts and the document header sections. Each export must persist its own rendered copy (text and referenced images) so it can be retrieved later even as the draft changes. Allow exporting any immutable light version and the latest draft only if it is clearly labelled as a draft. Existing full-course editors can export full courses in these document formats without granting light-role users full-course access. Document export does not replace the existing Adapt ZIP.

### 6. Versions, comparison and document import

Version comparison aligns stable IDs and highlights text, added/deleted/moved nodes and plugin selections. Old versions are read-only and exportable. Document import is for a light course's latest version only. Define one canonical document structure and an allowlist of supported HTML (for example paragraphs, headings, lists, emphasis and links); use structured Markdown and `.docx` parsers/writers, not regex substitutions. Embed stable machine-readable identifiers in both document formats and keep them out of editable prose. Reject missing/duplicated IDs, renamed structural headings, changed order, changed plugin choices and unknown fields with a location-specific error report; allow only text and supported formatting changes. Do not mutate the draft or create a version on a failed import. A successful import appends a new, auto-filled version history row (Date/Author/Screens/Words calculated, Notes/Est. duration left for the editor to complete) to the resulting draft. Provide round-trip fixtures for both formats, including escaping, Unicode, empty fields, nested items and HTML. This is controlled round-tripping, not lossless support for arbitrary Word styling.

### 7. Admin conversion

Convert only the latest published version, by full admin action; require no unversioned draft changes or prompt the admin to publish them first. Preflight component/plugin availability, required properties, defaults, image/audio/media assets, unique IDs, chosen button/help-screen icon identifiers against the target theme/menu, schema validation and tenant membership. Show actionable failures before any write. Create a normal full course and ordered content records using the existing course creation conventions, selecting one Menu/Theme, the chosen Extensions and component types. Assign left/right layouts for paired components, apply the chosen navigation icons where the theme/menu support them, and apply field-specific graphic/audio and other required defaults. Preserve all applicable translatable text and items. Where the glossary, resources and/or help extensions are selected, populate their configuration from the saved entries/content, carrying resource ID values through unchanged, and preflight-check that the extensions are actually installed before writing. Discard the remaining document header data (version history, reviewing instructions, developer information, terminology) and each component's Graphics Notes/Developer Notes - they stay on the light course for reference but are not written to the full course. Keep ID mappings for audit/troubleshooting.

Conversion must be idempotent for retries and behave atomically to users: either a validated full course exists and the light course is locked, or any partial full-course records/assets are cleaned up and the light course remains editable. Verify the generated course opens and validates before setting the converted state. Only a full administrator can edit the result. Older light versions remain reviewable, comparable and exportable after locking.

### 8. Verification and rollout

Add automated unit tests for schema traversal, counts (including notes/header exclusion), version increments, version-history row creation on import/manual add, comparisons, import validation, default mapping, icon preflight/mapping, audio field gating, glossary/resource/help conversion and template cloning; API tests for tenant/role permissions, conflicts and failure recovery; and browser tests for the list, editor, reordering, documents, templates and conversion. Run existing course/asset/export tests to guard against regressions. Pilot with real installed components, plugins and two tenants. Migrate roles/config without changing existing courses, add user/admin instructions, and release behind a feature flag if the deployment supports one.

## Acceptance scenarios

1. A light editor creates a titled course, sees it in a tenant-wide list, adds the full hierarchy, reorders blocks/components, saves a draft and publishes 1.0; another editor in the same tenant can access it, but another tenant cannot.
2. Two simultaneous saves do not silently overwrite one another; only one publication from a given latest version succeeds. Versions 1.0, 1.1 and 2.0 are immutable and comparisons report content, structure and plugin changes.
3. Installed components, nested translatable items, unique IDs and graphics are editable as described; missing plugin metadata stays visible read-only, and newly translatable fields appear after an upgrade.
4. A light editor adds an image to the bank and detaches it from a course, but cannot delete the bank image even by direct API request. Media defaults remain admin-managed.
5. Markdown and Word exports include counts; edited text and supported formatting can be imported against the latest version. Reordered nodes or altered identifiers in either document produce specific errors and no partial changes.
6. Full-course editors can view counts and export Markdown/Word for full courses; the light role cannot read or export those courses.
7. Only a full admin can convert the latest published version. A missing plugin/default or failed write does not lock the light course or leave a usable partial full course. Successful conversion creates a valid editable full course and locks only the light course.
8. A light editor adds glossary terms and resource entries, including resource ID values, to a course that has those extensions selected; conversion carries them into the new full course's extension configuration unchanged. Attempting to add either list to a course without the matching extension selected is blocked with an explanation.
9. An admin creates a template from an existing light course version. A light editor creates a new course from that template and gets a populated, independently editable draft; later edits to the new course or to the template do not affect one another.
10. A light editor edits the help extension's popup text and linked page content on a course that has the extension selected; conversion carries that content into the new full course unchanged. The editor is hidden on a course without the help extension selected.
11. A light editor fills in the document header sections and a component's Graphics Notes/Developer Notes, re-imports an exported document and sees an auto-filled version history row appended. None of this header data or the notes fields appear in word counts, and none of it is written to the full course on conversion, except that the chosen button/help-screen icons are applied to the generated full course's navigation.
12. A light editor adds audio to a component/item on a course with an audio extension selected; the field is hidden when that extension isn't selected. Conversion rejects a course whose chosen navigation icon isn't supported by the target theme/menu, with an actionable error and no partial write.

## Implementation decisions, resolved

The schema/codebase spike (Phase 1) has been run against this repository's actual conventions and the real installed Adapt framework checkout (found under `temp/<jobId>/adapt_framework/src`, containing the real `adapt-aleido-*`/`adapt-contrib-*` components, extensions, menus and themes - not placeholder schemas). Each item below replaces the corresponding open question; full detail and file references are in [Phase 1](LIGHT_COURSE_PHASE1_SCHEMA_SPIKE.md).

- **uniqueId storage**: resolved. `adapt-aleido-uniqueId` stores its value at `_extensions._uniqueId._id` on `contentobject` and `component` documents (course-level is only an enable toggle, no ID). Editor-facing `uniqueId` maps to this path, not a top-level field.
- **Audio extension schema**: resolved. `adapt-aleido-audio/properties.schema` declares distinct `pluginLocations.component._audio` (component-level) and a nested items block (item-level) sections; both must be walked separately from the common component fields.
- **Glossary/resources course-level configuration**: resolved. Both extensions patch the `course` schema (2020-12 `$patch`/`$anchor` dialect, not the AT draft-04 `model.schema` dialect). Glossary terms live at `_glossary._glossaryItems[]` (`term`, `description`). Resources config lives at `_resources` (`title`, `description`, `_resourcesItems[]`, etc.) and is declared at **both** course and content-object level, concatenated at render time; **confirmed no stable per-item ID exists anywhere in the schema or runtime** (`adapt-contrib-resources`'s `ResourcesView.js` resolves items purely by array index) - Phase 4's resource-entry editor must mint and persist its own stable ID per item. Both extensions are added via course-level config, not a separate creation step, so they can be toggled after course creation.
- **Help extension configuration**: resolved. The installed `adapt-aleido-help` only has one `_popup` (`title`/`body`/`instruction`) plus an `_items[]` array (icon/title/body/graphic per item) - **there is no separate "linked help page" content node and no style-toggle field** in the installed schema. Product decision: scope the help editor down to the real `_popup` + `_items` shape (Phase 4/7); no newer extension version is being waited on.
- **Button/help-screen icon configuration**: resolved, with a significant gap. Icon choice is **not** owned by the theme or menu at all - neither `adapt-contrib-vanilla` nor `adapt-theme-aleido` expose a navigation-icon schema. Instead each nav-contributing *extension* owns its own `_icon` Select with its own option list (`adapt-aleido-menuButton`: 9 options, `adapt-aleido-reflection`: 5 options, `adapt-aleido-help`: 2 options). The side-drawer icon is a freeform `_config._drawer._iconClass` text field, not a constrained Select. **The Back button has no configurable icon anywhere in the schema** - it's a fixed CSS class. Conversion preflight (Phase 7) must validate each chosen icon against its *owning extension's* option list individually, not against a single shared theme/menu list, and the Back control must be treated as fixed/non-configurable rather than erroring. Full per-control path/option-list table built in [Phase 1](LIGHT_COURSE_PHASE1_SCHEMA_SPIKE.md#per-control-buttonhelp-screen-icon-validation-table).
- **Draft replacement on import / draft export**: resolved as a product decision, not a schema fact: Phase 6 requires explicit confirmation before replacing an unsaved draft; draft (not just version) export is in scope since review instructions/header data must be exportable before a version exists.
- **Conversion cleanup/transactions**: resolved at the pattern level. `plugins/output/adapt/importsource.js` is the existing, working reference for "build real `course`/`contentobject`/`article`/`block`/`component` Mongo documents with correct parent-ID remapping and asset import from an external representation" - conversion (Phase 7) should reuse its ID-remapping and content-creation approach rather than building a parallel mechanism, wrapped in the same explicit cleanup-on-failure behaviour described in that phase.
- **Templates storage/versioning**: resolved as a product decision: a template is a single current content snapshot per record (no template-level version history), tenant-scoped like everything else in this plan, implemented as its own small content-plugin collection (see Phase 2).
- **Schema dialect split**: new finding, not in the original list. AT's own `model.schema` files (draft-04, flat `"translatable": true`) and the framework's `course.schema.json`/extension `properties.schema` files (two different dialects: draft-04 `properties.schema` for most extensions, 2020-12 `$patch` for course-schema-patching extensions like glossary/resources, each using a *different* translatable-marker convention: flat `"translatable": true` vs. nested `"_adapt": {"translatable": true}`) all need to be walked by the same word-count/import-export traversal. This traversal does not exist yet anywhere in the codebase (confirmed by repo-wide search) and must be built new in Phase 5, handling both dialects explicitly.

- **Document ID embedding**: resolved as a product decision. Markdown uses an invisible `<!-- lcid:<nodeId> -->` HTML comment above each heading/block; `.docx` uses a named Word bookmark (`lcid_<nodeId>`) wrapping each heading/paragraph. Both are invisible by default and fail safe - a missing/duplicated marker on import is a structural-validation error, never a guessed mapping. Full detail in [Phase 5](LIGHT_COURSE_PHASE5_WORDCOUNTS_EXPORTS.md).
- **Asset-usage indicator**: resolved as a product decision. Light-course asset usage stays separate from the existing full-course asset-usage scan for now (its own "used in this course" indicator sourced from `lightcoursebankasset`); unification is deferred until real usage shows editors need a single cross-cutting view. Full detail in [Phase 4](LIGHT_COURSE_PHASE4_COMPONENTS_PLUGINS_IMAGES.md).

No remaining open product decisions at this time; any new gaps found during implementation should be recorded here and routed back to the Light Editor team the same way.
